# Методика

## Вопрос

Можно ли, имея только открытый исходный код и документацию ArduPilot, получить побитово ту же
прошивку, что опубликована на [firmware.ardupilot.org](https://firmware.ardupilot.org), и при
каких условиях. Положительный ответ означает, что для реальной цепочки выпуска ПО
киберфизической системы (автопилота БВС) выполнимы свидетельства s23 «воспроизводимая сборка» и
s24 «независимая контрольная пересборка» графа доказательств SCII
([scii-gate](https://github.com/alexqzm/scii-gate)): проверяющий, которому поставщик ничего не
передаёт, может сам пересобрать выпуск и сравнить дайджесты.

Сборка считается воспроизводимой в смысле
[reproducible-builds.org](https://reproducible-builds.org/docs/definition/): из тех же исходного
кода, среды и инструкций любой получает побитово одинаковые артефакты. Артефакт здесь — файл
`.apj`, который загружают в автопилот наземные станции, и образ внутренней флеш-памяти внутри
него.

## Генеральная совокупность и выборка

Совокупность — стабильные выпуски, перечисленные в манифесте firmware.ardupilot.org
(`manifest.json.gz`). Снимок манифеста лежит в
[`data/manifest-2026-11-06.json.gz`](../data/manifest-2026-11-06.json.gz): загружен 06.11.2026 в
18:00 UTC, Last-Modified сервера — 06.11.2026 17:14:26 GMT, SHA-256
`ca5c3a1cc65baa5d8412babfb3a1be4a933bdb32d152e4565285a8d6b8b94b6a`, 103 265 записей.

**Выпуски.** Последний выпуск каждой стабильной линейки 4.4–4.7 для Copter, Plane и Rover:
Copter и Plane 4.4.4, 4.5.7, 4.6.3, 4.7.2; Rover 4.4.0, 4.5.7, 4.6.3, 4.7.2. Всего 12 групп
«изделие × выпуск». Варианты с другим именем файла (`arducopter-heli.apj` и т. п.) в выборку не
входят.

**Платы.** В каждой группе — восемь плат постоянной панели, если выпуск для них есть, и четыре
случайные платы из остальных. Панель — распространённые платы разных семейств STM32 (выбор
автора): CubeOrange, CubeOrangePlus, Pixhawk6X, MatekH743 (H7); Pixhawk4, CubeYellow (F7);
CubeBlack, MatekF405-Wing (F4). Случайная часть детерминирована: платы ранжируются по SHA-256
строки `зерно:изделие:версия:плата`, берутся первые четыре. Зерно — SHA-256 снимка манифеста:
его не выбирал автор, и выбор может повторить кто угодно.

**Группа «из тега».** Тринадцатая группа, `Copter-4.6.3-tag`, собирает панель из коммита тега
`Copter-4.6.3`, а не из коммита, указанного в официальных файлах (см. «Находки до прогона»).

План — 13 групп, 152 сборки — зафиксирован в [`plans/study-2026-11.json`](../plans/study-2026-11.json)
до основного прогона. CI проверяет, что план заново получается из снимка манифеста и тегов
ArduPilot.

## Процедура

Для каждой платы группы (`aprepro run`):

1. **Исходный код.** Коммит, указанный в манифесте для этой прошивки, забирается по SHA
   (`git fetch --depth 1 origin <sha>`), подмодули — на закреплённых в дереве коммитах. Тег
   используется только для сравнения с коммитом.
2. **Официальные файлы.** `.apj`, `git-version.txt` и `firmware-version.txt` из каталога прошивки
   на firmware.ardupilot.org; при расхождении — ещё `.elf` для разбора.
3. **Тулчейн.** `gcc-arm-none-eabi-10-2020-q4-major` (GCC 10.2.1 20201103): его задаёт
   `Tools/environment_install/install-prereqs-ubuntu.sh` во всех четырёх линейках. Архив берётся с
   firmware.ardupilot.org и сверяется с SHA-256
   `21134caa478bbf5352e239fbc6e2da3038f8d2207e089efc96c3b55f1edcd618`. ArduPilot контрольных сумм
   рядом с архивом не публикует; значение измерено при первой загрузке и совпадает с закреплённым
   в scii-gate.
4. **Python.** 3.11 для линеек 4.5–4.7 и 3.10 для 4.4: waf из ArduPilot 4.4 открывает файлы в
   режиме `'rU'`, убранном в Python 3.11. Пакеты из `install-prereqs-ubuntu.sh`, нужные сборке
   (empy 3.3.4 и др.), — с закреплёнными версиями и хешами,
   [`ci/requirements-build.txt`](../ci/requirements-build.txt). Интерпретатор должен быть собран с
   классическим zlib (см. ниже); CI это проверяет.
5. **Сборка.** Каталог `build/` удаляется, затем `./waf configure --board <плата>` и
   `./waf copter|plane|rover` — параметры по умолчанию, как у штатной сборки.
6. **Сверка.** Вердикт: `reproducible` — файлы `.apj` побитово совпадают; `image-identical` —
   совпадают образы, различаются метаданные `.apj`; `not-reproducible` — образы различаются;
   `error` — сборка или загрузка не удались. Для различающихся образов записываются области
   различий и печатные строки рядом с ними, а по файлам ELF — символы, различающиеся размером, и
   разбор блоков ROMFS.
7. **Чувствительность к zlib.** Для каждой прошивки из официального ELF извлекаются блоки ROMFS;
   содержимое каждого сжатого блока пережимается zlib среды прогона и zlib-ng (привязки
   [zlib-ng](https://pypi.org/project/zlib-ng/) для Python) с параметрами `embed.py` и сравнивается
   с официальным потоком. Сборки для этого не нужны, поэтому проверка охватывает все прошивки
   выборки.
8. **Аттестация.** Утверждение in-toto v1 с предикатом `urn:scii:predicate:rebuild:v1` — тем, что
   scii-gate проверяет у s23 и s24: коммит, SHA-256 тулчейна, кто пересобирал, дайджест
   пересобранного образа и проверяемого, итог MATCH или MISMATCH. В CI по желанию подписывается
   бесключевой подписью Sigstore (cosign; запись в публичном журнале Rekor).

Отдельно для каждой группы сопоставляются коммит тега и коммит сборки, тип выпуска в
`firmware-version.txt` и тип, зашитый в образ (структура `AP_FWVersion`).

**Среда основного прогона:** GitHub Actions, `ubuntu-24.04`, Python из `actions/setup-python`
(версия — из плана группы). Каждая группа — отдельная задача; версия zlib интерпретатора,
компилятор и число ядер записываются в `results/<план>/<группа>/_group.json`.

Первый запуск (42274617056, 06.11.2026) прерван: инструмент удалял после сборки только каталог
платы, и waf отказывался собирать следующую плату группы, а для линейки 4.4 не подходил Python
3.11. План изменён до получения результатов только в части исполнения (поле `python` групп);
состав групп и плат прежний. Результаты первого запуска не используются.

## Находки до прогона

**Реализация zlib в интерпретаторе Python влияет на прошивку.** ArduPilot встраивает в прошивку
файлы ROMFS (загрузчик, параметры по умолчанию, `hwdef.dat`, прошивку сопроцессора) и сжимает их
при сборке средствами интерпретатора (`Tools/ardupilotwaf/embed.py`): до 4.5 включительно —
`gzip.GzipFile(compresslevel=9, mtime=0)`, с 4.6 — `zlib.compressobj(level=9, wbits=-15,
memLevel=9)`. В обоих случаях сжимает библиотека zlib, с которой собран Python, а классический
zlib и zlib-ng дают для одного содержимого разные потоки deflate. Проверка на Copter 4.7.2 для CubeOrange (коммит `fb773567`),
06.11.2026, на машине, где интерпретаторы Python собраны с zlib-ng 1.3.1:

- сборка с zlib-ng: образ на 112 байт длиннее официального (1 645 148 против 1 645 036),
  1388 областей различий, 214 798 различающихся байт — сдвиг адресов после блоков ROMFS;
- по таблицам символов ELF размером различаются только пять блоков `ap_romfs_0…4`; их
  распакованное содержимое совпадает с официальным побитово;
- официальные блоки побитово совпадают с выводом классического zlib 1.3.2 (Python 3.11 из
  python-build-standalone) и не совпадают с выводом zlib-ng;
- сборка того же дерева интерпретатором с классическим zlib 1.3.2 дала файл `.apj`, побитово
  совпадающий с официальным (SHA-256 `95ab5dee46134dd1…`).

У Copter 4.5.7 для CubeOrange (ROMFS в gzip) по официальному ELF: классический zlib 1.3.2
воспроизводит все пять блоков, zlib-ng — только самый короткий (`defaults.parm`, 268 байт).

Зависимость от реализации zlib не упомянута в `install-prereqs-ubuntu.sh`: там закреплены тулчейн
и empy, но не библиотека, с которой собран Python. В дистрибутивах, где zlib заменён zlib-ng
(в Fedora — с версии 40, [Changes/ZlibNGTransition](https://fedoraproject.org/wiki/Changes/ZlibNGTransition);
там же отмечено, что сжатый вывод zlib-ng может отличаться от zlib), штатная сборка с ROMFS не
воспроизводит официальную прошивку.

**Тег Copter-4.6.3 не указывает на коммит официальной сборки.** Все 236 прошивок Copter
stable-4.6.3 с файлом `.apj` в манифесте собраны из коммита `3fc7011a` («Plane: version to
4.6.3», 03.11.2025). Тег `Copter-4.6.3` указывает на `92b0cd78` («Copter: version to 4.6.3
official fix», 11.11.2025), который меняет одну строку `ArduCopter/version.h`:
`FW_TYPE FIRMWARE_VERSION_TYPE_BETA` → `FIRMWARE_VERSION_TYPE_OFFICIAL`. В образе официальной
прошивки для CubeOrange структура `AP_FWVersion` содержит тип BETA, а `firmware-version.txt`
рядом — `4.6.3-FIRMWARE_VERSION_TYPE_OFFICIAL`. Проверяющий, который пересоберёт выпуск из тега,
получит другой образ.

## Ограничения

- Выборка: три изделия, четыре линейки, 12 плат на группу; Sub, вертолётные варианты, Tracker,
  AP_Periph и форматы кроме `.apj` (`.hex` с загрузчиком, `.abin`) не проверялись.
- Среда официального сервера сборки не опубликована; реализация zlib на нём выведена из того,
  какой вывод совпадает.
- SHA-256 тулчейна закреплён по первой загрузке (доверие при первом использовании).
- Результат относится к файлам на сервере на дату прогона; ArduPilot может пересобрать и
  заменить файлы выпуска.
- Совпадение подтверждает, что прошивка получается из указанного коммита этим тулчейном, а не что
  исходный код безопасен.

## Связь с SCII

- **s23, s24.** Независимая пересборка выполнима для реальной прошивки КФС, если проверяющий
  знает три входа: коммит (из `git-version.txt` или `git_identity`, а не тег), тулчейн и
  реализацию zlib интерпретатора. Третий вход не входит в документированную среду сборки;
  аттестация происхождения, которая его не перечисляет, неполна.
- **s14.** Случай Copter 4.6.3: подписанный тег (у ArduPilot теги лёгкие и неподписанные) не
  связал бы опубликованный образ с исходным кодом — тег указывает на другой коммит.
- **s52.** Тип выпуска входит в номер версии svn квитанции SCII-R v1 (`fw_type`); у Copter
  4.6.3 он в образе BETA, хотя выпуск стабильный.
